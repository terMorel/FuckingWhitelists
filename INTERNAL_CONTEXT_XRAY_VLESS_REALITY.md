# Внутренний контекст: Frankfurt VPS + Xray/VLESS Reality

## Дополнение: отдельная панель нативного Hysteria2

Для рабочего нативного Hysteria2 выбран отдельный контур управления `Fucking Whitelists Control` (`hyboard/`). Панель не переносит Hysteria внутрь Xray/3x-ui и не участвует в передаче трафика.

```text
VPN data plane: клиент -> Hysteria2 UDP/443 -> hysteria-server -> Internet
Management: браузер -> SSH tunnel -> HyBoard -> group-only Unix socket -> root broker -> hy-access -> users.json
```

Инженерные ограничения:

- не менять UDP/443, TLS, Salamander, masquerade и командную авторизацию рабочего Hysteria2;
- не перезапускать Hysteria для создания, ротации или отзыва пользователя;
- не давать панели доступ к WireGuard, Xray, firewall или произвольным root-командам;
- не использовать `sudo` из веб-процесса: привилегированные операции идут через отдельный root-broker без сетевого порта и с Unix-сокетом `root:hyboard 0660`;
- использовать существующий `/usr/local/sbin/hy-access` как единственную точку изменения пользователей;
- публиковать только исходный код и placeholders, никогда не IP, токены, QR, пароль панели и содержимое `users.json`;
- по умолчанию слушать только `127.0.0.1` и открывать панель через SSH-туннель.

Панель может быть остановлена без остановки VPN. Сроки доступа реализуются отдельным systemd-таймером, который отзывает пользователя через тот же `hy-access`.

## 1. Второй контур проекта: личный VPS VPN

В проекте появился отдельный сценарий помимо FreeTurn/WireGuard:

Цель:

- личный зарубежный VPS;
- доступ для нескольких доверенных пользователей;
- высокая скорость по сравнению с аварийным TURN-каналом;
- использование Xray/VLESS Reality.

```text
Телефон
  ↓
V2RayTun / v2rayNG / другой Xray-клиент

Frankfurt VPS
  ↓

  ↓

```

## 5. Объяснение терминов для внутреннего контекста

### Почему это ближе к proxy, а не к классическому VPN

Текущая схема технически ближе к proxy-туннелю:

```text
Phone app → local VPN interface → VLESS client → Xray server → outbound Internet
```

Причины:

- VLESS — протокол семейства V2Ray/Xray для проксирования соединений;
- Xray на сервере принимает клиентское подключение и от имени сервера открывает соединения дальше;
- нет отдельной классической VPN-сети вида `10.8.0.0/24`, как в OpenVPN/WireGuard;
- маршрутизация по приложениям/доменам в основном решается клиентом на телефоне;
- приложение на Android/iOS создаёт локальный VPN-интерфейс, поэтому для пользователя это выглядит как VPN.

Практический вывод:

- бытовое название «VPN» допустимо;
- технически точнее: `Xray VLESS Reality proxy tunnel`;
- защищённый туннель между телефоном и VPS всё равно есть.

## 6. Что даёт защита на чужом Wi-Fi

Если V2RayTun/VLESS Reality включён и весь нужный трафик идёт через туннель, владелец чужой Wi-Fi-точки видит главным образом:

```text
client_device → SERVER_IP:443
```

Он не должен видеть содержимое трафика внутри туннеля.

Ограничения:

- VPN/proxy не защищает от фишинга;
- не защищает от вредоносных приложений на телефоне;
- split tunneling может пустить часть приложений напрямую;
- DNS leaks возможны при неправильной настройке клиента;
- HTTPS всё равно важен: выходной VPS не должен становиться точкой чтения незашифрованного HTTP.

## 7. Проблема, возникшая 10.07.2026

Симптом:

- ранее VLESS Reality работал;
- затем перестал работать из некоторых российских сетей;
- возникла гипотеза, что РКН/DPI начал ограничивать такие подключения.

Важно:

Нельзя сразу считать, что «VLESS полностью заблокирован».
Возможные причины:

1. DPI/traffic shaping по поведению соединения;
2. ограничения TCP 443;
3. блокировка или ухудшение маршрута до зарубежного VPS;
4. несовместимость клиента и Reality-конфига;
5. старый клиентский профиль после смены Reality-ключей;
6. проблемы с target/SNI;
7. случайно заполненные `Min Client Ver` / `Max Client Ver`.

## 8. Диагностика

Проверки:

### Проверка процесса

```bash
ss -tulpn | grep ':443'
```

Ожидается `xray` в состоянии `LISTEN`.

### Проверка доставки пакетов

```bash
tcpdump -i any port 443
```

Если пакеты доходят:

- IP не полностью заблокирован;
- TCP-порт не полностью заблокирован;
- проблема, вероятно, выше сетевого уровня: Reality handshake, клиентский профиль, target/SNI, DPI по паттерну потока или другое поведение после установки TCP-соединения.

### Логи

```bash
journalctl -u x-ui -f
```

Важно различать:

- обращения к панели 3x-ui;
- реальные Xray/VLESS соединения;
- случайные сканирования панели;
- попытки входа в админку.

## 9. Фактическая диагностика 10.07.2026

Проведены команды:

```bash
ss -tulpn | grep ':443'
ufw status
tcpdump -i any port 443
```

Зафиксировано:

```text
xray listens on TCP 443
UFW status: inactive
client packets reach SERVER_IP:443
server replies with SYN-ACK
client sends payload around 1500 bytes
server opens outbound HTTPS connection to configured Reality target/CDN side
server receives a very small response and closes the connection quickly
```

Интерпретация:

- это не выглядит как полная блокировка IP сервера;
- это не выглядит как полная блокировка TCP/443 до сервера;
- пакеты с клиента физически долетают до VPS;
- дальше соединение быстро схлопывается, поэтому основная гипотеза — проблема на уровне Reality/Xray/client profile/target-SNI либо DPI по характеру установленного TCP-потока.

Отдельно зафиксировано:

- `ufw status` показал `inactive`;
- поэтому команды `ufw allow ...`, `ufw delete allow ...`, `ufw reload` не применяют firewall-политику, пока UFW не включён;
- включать UFW следует только после проверки доступов, чтобы не потерять SSH/панель.

## 10. Безопасность панели 3x-ui

В логах панели были видны failed/successful login events.

Если успешные входы не принадлежат владельцу, нужно считать панель скомпрометированной.

Минимальный план реагирования:

1. сменить пароль 3x-ui;
2. сменить web base path;
3. сменить порт панели;
4. проверить список клиентов;
5. удалить неизвестные inbounds/clients;
6. перегенерировать Reality private/public keys;
7. заново выдать клиентские профили;
8. не публиковать screenshots с private key, UUID, QR и panel path.

Даже если входы были владельца, порт панели не должен быть «вечной публичной дверью». Желательно ограничить доступ к панели или хотя бы регулярно менять пароль/path и не держать очевидный порт.

## 11. Ближайший план восстановления VLESS Reality

Порядок действий без разрушения текущей конфигурации:

1. Не удалять текущий inbound.
2. Проверить вкладку `Security` у текущего inbound.
3. Убедиться, что `Security = Reality`.
4. Установить стабильную пару `Target/SNI`, например `www.microsoft.com:443` + `www.microsoft.com`.
5. Очистить `Min Client Ver` и `Max Client Ver` полностью.
6. Проверить `uTLS = chrome`.
7. Проверить `SpiderX = /`.
8. Перегенерировать Reality keys.
9. Сохранить изменения.
10. Перезапустить сервис:

```bash
systemctl restart x-ui
```

11. Проверить, что Xray снова слушает порт:

```bash
ss -tulpn | grep ':443'
```

12. Удалить старый профиль в Android-клиенте.
13. Заново экспортировать QR/Android key/VLESS profile.
14. Импортировать новый профиль.
15. Повторить `tcpdump -i any port 443` во время подключения.

Критерий улучшения:

- вместо короткого соединения на 1–2 секунды появляется продолжительный поток пакетов;
- `2ip`/проверка внешнего IP показывает выход через VPS;
- приложения начинают открывать внешние сайты.

Порядок экспериментов:

### Вариант 1. Новый VLESS inbound на другом TCP-порту


---

### Вариант 2. Hysteria2 на том же VPS

Рассмотреть как альтернативный транспорт:

```text
VLESS Reality TCP
+
Hysteria2 QUIC/UDP
```

Плюсы:

- другой транспорт;
- не зависит от TCP 443 сценария.

Минусы:

- может быть ограничен UDP;
- нужен отдельный клиентский профиль;
- если оператор режет зарубежный UDP/QUIC, прямой Hysteria2 до Frankfurt тоже может не помочь.

---

### Вариант 3. XHTTP + Reality

Рассматривать после резервного копирования.

Причина:

- современный транспорт Xray;
- другая модель передачи данных;
- потенциально меньше похож на один долгоживущий TCP-поток.

Нужно проверять совместимость клиента.

## 13. Возможная схема через российский relay

Сценарий друга:

```text
Телефон
 ↓ Hysteria2 / другой внешний первый транспорт
Российский VPS / разрешённая инфраструктура
 ↓ второй участок
Frankfurt VPS
 ↓
Internet
```

Важное понимание:

ценность может быть не в Yandex Cloud как таковом, а в том, что первый адрес назначения является доступным российским узлом из текущей сети/режима ограничений.

Однако случайный российский VPS не гарантирует тот же результат.

Лучший вариант:

- первый узел принимает соединение;
- второй участок остаётся зашифрованным;
- не использовать незашифрованный HTTP между узлами;
- если relay только пересылает L4-поток, он не должен иметь пользовательские ключи содержимого.
