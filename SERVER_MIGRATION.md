# Перенос Hysteria2 и HyBoard на другой сервер

Этот документ описывает воспроизводимый перенос основного VPN-контура: нативного Hysteria2, персональных доступов, HyBoard, статистики и защищённого доступа к панели. Скрипты не изменяют рабочий сервер при создании бэкапа и не переносят автоматически Xray/3x-ui или FreeTurn/WireGuard.

## Что хранится где

GitHub содержит код, инструкции, systemd-шаблоны и инструменты восстановления. Секреты в Git не помещаются.

Отдельный зашифрованный recovery bundle содержит:

- конфигурацию Hysteria2, пользовательские credentials и сертификаты из `/etc/hysteria`;
- точный исполняемый файл Hysteria и его контрольную сумму;
- `hy-access` и его данные;
- конфигурацию HyBoard, согласованную копию SQLite и секрет Traffic Stats API;
- unit-файлы и вспомогательные команды мониторинга;
- конфигурацию Nginx и Let's Encrypt как материал для ручной адаптации;
- SSH-конфигурацию без host private keys, `authorized_keys`, UFW и sysctl как материал для ручной адаптации;
- найденные каталоги `hyboard-client-pki-*`, включая `.p12` и зашифрованный ключ CA, если они есть на сервере;
- инвентаризацию версий, служб, портов и контрольных сумм;
- дополнительные явно указанные каталоги.

Recovery bundle содержит действующие секреты. Его можно хранить в облаке только в виде `.age`, но нельзя коммитить даже в приватный Git-репозиторий. Приватность репозитория и пароль `.p12` не заменяют шифрование всего набора.

## 1. Один раз создать офлайн-ключ шифрования

На доверенном ноутбуке установите `age` и создайте identity:

```bash
age-keygen -o hyboard-recovery-identity.txt
age-keygen -y hyboard-recovery-identity.txt
```

Первая команда создаёт секретный identity-файл. Вторая печатает публичный recipient вида `age1...`.

- identity храните только вне VPS: например, в менеджере паролей и на зашифрованной флешке;
- на сервер передаётся только публичный recipient;
- потеря identity означает невозможность расшифровать бэкап;
- утечка identity означает необходимость создать новый ключ и новый bundle.

## 2. Создать bundle на исходном сервере

Установите `age`, обновите копию репозитория и выполните:

```bash
sudo apt-get update
sudo apt-get install -y age
cd /root/FuckingWhitelists
sudo bash deploy/create-recovery-bundle.sh \
  --recipient 'age1PUBLIC_RECIPIENT' \
  --output /root/hyboard-recovery/recovery-$(date -u +%Y%m%dT%H%M%SZ).age
```

Скрипт:

1. проверяет наличие обязательных файлов;
2. делает SQLite online backup без остановки панели;
3. собирает данные во временном каталоге с правами root-only;
4. создаёт manifest SHA-256;
5. шифрует архив публичным age-recipient;
6. удаляет временную открытую копию.

Сохраните напечатанный SHA-256 в менеджере паролей отдельно от `.age`. Age-recipient является публичным и не доказывает, кто создал архив; отдельная контрольная сумма защищает от подмены bundle перед исполнением сохранённого бинарного файла.

Для отдельного контура можно добавить точный путь, но только после его собственной проверки:

```bash
sudo bash deploy/create-recovery-bundle.sh \
  --recipient 'age1PUBLIC_RECIPIENT' \
  --output /root/hyboard-recovery/recovery-full-$(date -u +%Y%m%dT%H%M%SZ).age \
  --extra-path /etc/wireguard
```

`--extra-path` только помещает данные в шифрованный архив. Скрипт восстановления основного контура эти данные автоматически не применяет.

Скачайте `.age` на ноутбук через `scp` или SFTP. После подтверждения загрузки удалите серверную копию, если не хотите хранить там второй экземпляр.

## 3. Обязательно проверить бэкап вне сервера

На доверенной Linux-машине или в WSL:

```bash
bash deploy/verify-recovery-bundle.sh \
  --bundle recovery-YYYYMMDD.age \
  --identity hyboard-recovery-identity.txt \
  --expected-sha256 'SHA256_ИЗ_МЕНЕДЖЕРА_ПАРОЛЕЙ'
```

Успешное создание файла ещё не является проверенным бэкапом. Минимум два экземпляра `.age` должны находиться на разных носителях, а identity — отдельно от них.

Рекомендуемый график:

- после изменения Hysteria, Nginx, mTLS или состава пользователей;
- перед любым рискованным обновлением;
- планово раз в месяц;
- проверка расшифрования каждого нового bundle;
- тестовое восстановление на временном VPS не реже одного раза в квартал.

## 4. Подготовить чистый новый VPS

Для автоматического core restore нужен чистый Ubuntu 22.04/24.04 без существующих `/etc/hysteria/config.yaml`, `/etc/hyboard/hyboard.env`, `/var/lib/hyboard/hyboard.db` и `/root/hysteria-access`.

1. Обновите ОС и настройте SSH/firewall.
2. Устанавливать Hysteria заранее необязательно: проверенный бинарный файл той же версии находится в bundle. Если Hysteria уже установлена, скрипт потребует полного совпадения бинарного файла.
3. Установите `age`, `git`, Python и Nginx.
4. Клонируйте этот репозиторий.
5. Передайте `.age` и временно identity на новый VPS по защищённому каналу.

Не запускайте восстановление поверх работающей системы: скрипт специально остановится, если увидит существующую конфигурацию.

## 5. Расшифровать только в root-only staging

```bash
sudo bash deploy/stage-recovery-bundle.sh \
  --bundle /root/recovery-YYYYMMDD.age \
  --identity /root/hyboard-recovery-identity.txt \
  --expected-sha256 'SHA256_ИЗ_МЕНЕДЖЕРА_ПАРОЛЕЙ' \
  --output /root/hyboard-restore-stage-YYYYMMDD
```

Команда проверяет структуру и все контрольные суммы, но ничего не меняет в `/etc`, `/opt` или systemd.

После staging удалите identity с VPS. Его постоянное место — офлайн-хранилище, а не сервер.

## 6. Восстановить основной контур на чистом сервере

```bash
sudo bash deploy/restore-new-server.sh \
  --stage /root/hyboard-restore-stage-YYYYMMDD \
  --repo /root/FuckingWhitelists \
  --apply
```

Скрипт восстанавливает только Hysteria2 и HyBoard, запускает службы и проверяет их состояние. Он не применяет сохранённые Nginx/Let's Encrypt/PKI, SSH, UFW или sysctl автоматически.

Причина: серверный TLS-сертификат связан с адресом. При новом IP старый сертификат обычно непригоден. Это относится и к Hysteria, если её TLS-сертификат выпущен для старого IP/домена. Конфигурацию доступа к панели нужно адаптировать и снова выпустить сертификат для нового адреса по [`HYBOARD_REMOTE_ACCESS.md`](HYBOARD_REMOTE_ACCESS.md). Клиентский `.p12` можно сохранить, если его приватный ключ не скомпрометирован и новый Nginx доверяет прежнему client CA.

## 7. Что происходит с пользовательскими ключами

Credentials Hysteria2 и obfuscation secret сохраняются, поэтому их не обязательно менять при плановом доверенном переносе. Но URI содержит адрес сервера:

- если публичный IP сохранился, старые URI могут продолжить работать;
- если IP изменился, в URI/QR нужно заменить адрес либо выдать новые ссылки;
- доменное имя вместо IP уменьшает объём изменений при следующем переносе;
- если старый VPS потерян или мог быть скомпрометирован, нужно ротировать все пользовательские credentials, obfuscation secret, пароль панели, session secret, stats secret и клиентский CA.

## 8. Проверка перед переключением

На новом сервере:

```bash
systemctl is-active hysteria-server.service hyboard.service
systemctl is-active hyboard-helper.service
systemctl is-active hyboard-expire.timer hyboard-monitor.timer
curl --fail http://127.0.0.1:28474/healthz
ss -lunp | grep ':443'
ss -ltnp | grep '28474'
```

Затем выполните реальный тест отдельным клиентом:

1. подключение устанавливается;
2. открываются несколько независимых сайтов;
3. внешний IP соответствует новому VPS;
4. YouTube/Telegram и обычный браузинг стабильны;
5. трафик и online-state появляются в HyBoard;
6. создание и отзыв тестового доступа работают;
7. HTTPS/mTLS панели проверен отдельно.

Не выключайте старый сервер до прохождения этих проверок.

## 9. Отдельные контуры

Xray/3x-ui и FreeTurn/WireGuard не являются частью автоматического core restore. Для них нужны отдельные baseline, backup и проверка. Их нельзя «восстановить заодно» изменением Hysteria или HyBoard: это увеличивает риск сломать оба независимых канала.

Порядок полного переезда:

1. Hysteria2;
2. HyBoard и статистика;
3. Nginx/mTLS панели;
4. Xray/3x-ui — только если нужен;
5. FreeTurn/WireGuard — последним и только по отдельной методике;
6. финальный inventory и новый recovery bundle.

## 10. Что сохранить владельцу

В менеджере паролей или зашифрованном хранилище должны быть:

- данные провайдера и доступ к его аккаунту;
- актуальный IP/домен, SSH-порт и административный пользователь;
- SSH private key и проверенный host fingerprint;
- пароль HyBoard и URL панели;
- age identity и его публичный recipient;
- местонахождение двух проверенных `.age` bundle;
- SHA-256 каждого bundle, сохранённый отдельно от самого файла;
- пароль `.p12`, сам `.p12` и recovery-набор client CA;
- список доверенных устройств и кому выдан каждый VPN-доступ;
- Telegram bot token/chat ID, если оповещения включены;
- дата последнего теста восстановления;
- ссылка на этот репозиторий и commit, работающий на сервере.

Не записывайте реальные значения в этот файл или в GitHub.
