# 8. Диагностика типичных проблем

[← Безопасность](07-security.md) · [Оглавление](../README.md)

Диагностируйте цепочку по уровням. Не меняйте сразу DNS, ключи, MTU и звонок: иначе невозможно понять причину.

## Быстрый чек-лист

```text
1. free-turn-proxy запущен?
2. Его внешний порт слушается?
3. Телефон достигает free-turn-proxy?
4. rtpopus и obf-key совпадают?
5. Есть WireGuard handshake?
6. Растут счётчики transfer?
7. Включены forwarding и NAT?
8. Совпадает ли внешний IP телефона с VPS?
9. Только после этого проверять MTU, DNS и скорость.
```

## `status=203/EXEC` или `Permission denied`

Служба не смогла запустить бинарник. Проверьте:

- существует ли файл;
- есть ли право исполнения;
- может ли пользователь службы читать каталоги по пути;
- не смонтирована ли файловая система с `noexec`;
- подходит ли архитектура бинарника.

Если бинарник вручную показывает справку, а служба нет, проблема находится в unit-файле или пользователе службы.

## `unknown port`

Адрес сервера введён в неправильном формате.

Правильно:

```text
SERVER_IP:56000
```

Неправильно:

```text
http://SERVER_IP
https://SERVER_IP
```

## `message authentication failed`

Характерный текст:

```text
rtpopus: AEAD open
chacha20poly1305: message authentication failed
```

Телефон уже достигает VPS, но клиент и сервер используют разные:

- `obf-key`;
- `obf-profile`;
- либо повреждённое значение с пробелом/кавычками.

Сверьте фактическую строку запуска службы с настройкой клиента. Для `rtpopus` ключ должен быть одной и той же 64-символьной hex-строкой.

## Статус активен, но handshake отсутствует

Статус приложения отражает только часть цепочки. Проверьте на VPS:

```text
latest handshake
transfer received/sent
```

Если входящие пакеты доходят до внешнего порта, но handshake нет, проверьте:

- импортирован ли правильный WireGuard-конфиг;
- `Endpoint = 127.0.0.1:9000`;
- `free-turn-proxy` передаёт на `127.0.0.1:51820`;
- публичные ключи peers;
- внутренний IP клиента;
- режим `udp` для WireGuard-backend.

## Handshake есть, интернета нет

Проверьте:

- `net.ipv4.ip_forward = 1`;
- правило NAT/MASQUERADE;
- правила FORWARD;
- маршрут по умолчанию VPS;
- `AllowedIPs = 0.0.0.0/0` на клиенте;
- DNS внутри VPN.

Если счётчики WireGuard растут только в одном направлении, ищите проблему маршрутизации или firewall.

## Google работает, тяжёлые сайты нет

Порядок проверки:

1. Убедиться, что внешний IP действительно равен IP VPS.
2. Снизить MTU, например с 1280 до 1120, и повторить тест.
3. Проверить потери и задержку.
4. Постепенно увеличить число потоков.
5. Один раз сравнить TCP и UDP внешний транспорт.

Если лёгкие страницы открываются, но скорость стабильно около 1 Мбит/с, это может быть пределом VK TURN/оператора, а не ошибкой конфигурации.

## CAPTCHA или вечное «Подключение»

Проверьте:

- действительна ли ссылка звонка;
- не завершён ли звонок для всех;
- доступен ли ручной режим CAPTCHA;
- не слишком ли много потоков;
- не ограничен ли аккаунт VK;
- работает ли официальный звонок через ту же мобильную сеть.

Не ждите бесконечно: отсутствие результата за 60–90 секунд обычно означает ошибку установления сессии.

## Случайные участники

Технические сессии могут отображаться случайными именами, но неизвестного участника нельзя автоматически считать безопасным.

Если участник:

- появляется без запуска FreeTurn;
- остаётся после остановки;
- включает звук или видео;
- пишет сообщения,

завершите звонок, смените ссылку и проверьте секреты.

## Финальное правило

Разделяйте:

```text
неисправность настройки
и
ограничение внешнего транспорта
```

Если весь маршрут технически работает, handshake стабилен, NAT исправен, но скорость остаётся низкой, бесконечная смена ключей и DNS не превратит аварийный медиатуннель в быстрый VPN.
